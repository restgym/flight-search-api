# Flight Search API for RESTgym

This repository is the RESTgym integration of Flight Search API. It is meant to be used as a Git submodule of [RESTgym](https://github.com/restgym/restgym) (in `apis/flight-search/`), which builds its Docker image and runs it with the testing tools: it does not work on its own.

More details (e.g., how 5XX responses are grouped into unique failures) are in the manifest, `restgym-api-manifest.yaml`.

## How RESTgym runs it

The image starts from the base image of RESTgym for Java 21 (`restgym/api-base:java21`), which contains the proxy and the collection of code coverage. MongoDB 6.0 runs in the container, empty at each start: the original repository provides no data (see "Integration"). The proxy authenticates the requests of the tools (`auth.py`): it signs in as the administrator that `entrypoint.sh` registers when the API is ready (before the proxy starts), adds the access token to every request, and signs in again before the token expires (see "Endpoints that may interfere with authentication"). The tools reach the API through the proxy of RESTgym, on port 9090.

## Changes made by RESTgym

### API

**Errors have their real status code, not 401 or 404.** The API hid its errors behind two status codes, so it never failed with 5XX:

- **401**: Spring forwards the errors that no handler of the API answers (e.g., the `NoSuchMethodError` of `GET /v3/api-docs`, paths without an operation such as `DELETE /api/v1/airports/`, unsupported methods, media types and `Accept`) to `/error`, which the security configuration of the API did not permit (`SecurityConfig`: only `/api/v1/authentication/**`, Swagger and `/actuator/**`). The token filter of the API does not run again for `/error`, so the request was not authenticated, and the API answered 401 (`AUTH ERROR`) to any such error.
- **404**: the handler of the exceptions of the API (`GlobalExceptionHandler`) answered 404 (`API ERROR`) to any `RuntimeException` without a handler of its own: also to the invalid requests that Spring answers with 400 (e.g., `Required request body is missing`, `JSON parse error`, the `ResponseStatusException` of the actuator), and to the errors of the server, such as `NullPointerException` (`Cannot invoke "...CustomPaging.getPageNumber()" because "this.pagination" is null`), `PatternSyntaxException` (`Illegal repetition near index 1`), `rawPassword cannot be null`, or the exceptions of jjwt on tokens that the API does not validate (`Invalid compact JWT string`, `JWT expired`).

RESTgym permitted `/error` in `SecurityConfig`, and changed `GlobalExceptionHandler` to answer 404 only to the exceptions of the API (classes of `com.example.demo`, e.g., `Flight not found!`), and to leave the others to Spring, as if the handler did not exist: 400 for invalid requests, the status of a `ResponseStatusException`, 500 for the rest. The other handlers of the API (e.g., the 400 of validation, 401, 403, the 404 of `AirportNotFoundException`, 409) are unchanged. The changes, in `SecurityConfig.java`:

```java
                                "/actuator/**",
                                // RESTgym: the errors are forwarded to /error, which answered 401 to every error (originally not permitted)
                                "/error"
```

(instead of `"/actuator/**"`), and in `GlobalExceptionHandler.java`, at the start of `handleRuntimeException`:

```java
        // RESTgym: 404 only for the exceptions of the API, the others are left to Spring (e.g., 400 for an unreadable
        // body, 500 for an unexpected error), as if this handler did not exist (originally 404 for every RuntimeException)
        if (!runtimeException.getClass().getName().startsWith("com.example.demo.")) {
            throw runtimeException;
        }
```

Only `SecurityConfig.class` and `GlobalExceptionHandler.class` changed, in `flightsearchapi.jar` and in `classes/` (2026-10): they were compiled with `javac --release 21 --enable-preview -g -parameters` and Lombok 1.18.36 (as by Maven with Spring Boot 3.4.1) against the libraries of the executable, which were not rebuilt. All the classes of the API compiled so from commit `3de6a55` are identical to those of the executable, except `FlightEntity` and its builder, which differ only in the order of their constant pool and in a cast in the `self()` that Lombok generates (differences of compilation, not of code).

The errors that the API leaves to Spring have the message of the exception in their body (`server.error.include-message=always`, in `entrypoint.sh`), as the answers of its handler did: RESTgym groups the 5XX into unique failures by this message (`server_errors` in the manifest). In the runs of October 2026 (in `results/`), with 401 and 404 only:

- the 127,172 responses 401 outside the authentication endpoints are errors: replayed on a sample, about 60% are 406 (e.g., `GET /actuator/prometheus` and `GET /actuator/heapdump` with `Accept: application/json`), the others mostly 404, 405 and 415, and about 1% 500;
- of the 396,637 responses 404, about 168,000 are invalid requests (400 with this change), and about 44,000 errors of the server (500); the others are real 404 (e.g., of the actuator, or `Airport not found!`).

Verified 2026-10: the executable differs from the build of commit `3de6a55` (Maven 3.9.9, JDK 21, `mvn package -DskipTests`; identical to the previous `flightsearchapi.jar`, in its 468 entries) only in `SecurityConfig.class` and `GlobalExceptionHandler.class` (the other 466 entries are identical), and the bytecode of these two differs only by the changes above (`/error` added to the permitted paths; the check of the package of the exception at the start of `handleRuntimeException`, which rethrows the other exceptions). The classes in `classes/` are identical to those in the executable.

### Specification

The API cannot serve its specification as packaged: the springdoc-openapi of the application (2.1.0, as in the `pom.xml` of the original repository since its first commit) is incompatible with its Spring Boot (3.4.1, Spring Framework 6.2; springdoc supports Spring Boot 3.4 since 2.7.0). `GET /v3/api-docs` fails with `NoSuchMethodError: 'void org.springframework.web.method.ControllerAdviceBean.<init>(java.lang.Object)'` (500; 401 in the original API, see above): the Swagger UI that the README of the original repository documents (`/swagger-ui/index.html`) loads, but cannot load the specification. The original repository has no specification file.

The original specification is therefore `original/flight-search-openapi.json` (OpenAPI 3.0.1): the specification served at `/v3/api-docs` by `flightsearchapi.jar` with springdoc-openapi 2.7.0 in place of 2.1.0 (and the libraries it requires: swagger-core 2.2.25, swagger-ui 5.18.2, webjars-locator-lite 1.0.1, jspecify 1.0.0, from Maven Central; nothing else changed), saved unchanged from the API running in its RESTgym container (2026-10). The executable of the API is not changed: the copy with springdoc 2.7.0 was only used to obtain the specification (`flightsearchapi.jar` still contains springdoc-openapi 2.1.0, verified 2026-10). The specification is generated from the code and the configuration of the authors (`OpenApiConfig.java`: title, security scheme `bearerAuth`), but by a newer springdoc than the one they declare, so details may differ from what a working 2.1.0 would generate; its server URL is `http://localhost:8080` because springdoc writes the URL of the request. `specifications/README.md` describes it too.

The specification given to the tools is `standardized/flight-search-openapi.json`: the original, formatted, with two changes (in detail in `specifications/README.md`):

- **`in: header` removed from the security scheme `bearerAuth`** (validation error): it is of type `http`, for which OpenAPI 3.0 allows no `in` (the JWT goes in the `Authorization` header either way).
- **The 25 operations of Spring Boot Actuator removed** (`/actuator` and the 21 paths under it, e.g., `GET /actuator/health`, `GET /actuator/metrics`, `GET /actuator/heapdump`, `POST /actuator/loggers/{name}`, `DELETE /actuator/caches`; 40 operations in the original, 15 in the standardized specification): they are endpoints of the framework for monitoring and management (the original configuration exposes all of them, `management.endpoints.web.exposure.include: "*"`, and documents them, `springdoc.show-actuator: true`), not operations of the API. With them, the tools would spend a large part of their requests on operations that do not reflect the behavior of the API, and the coverage of the operations would count them. The API still serves them (its configuration is not changed).

The corrected specification, `corrected/flight-search-openapi.json`, is the standardized one with the fixes that make it match the implementation of commit `3de6a55` (found in its code and verified at runtime, 2026-10): the paging request of `GET /api/v1/airports` and `GET /api/v1/flights` as a required request body (not a query parameter), `pagination` and its `pageNumber` and `pageSize` required, `format: uuid` for the path parameter `id`, `format: date` for the dates of the search, `format: email` for the email of the registration, the bearer token required by the 11 operations outside `/api/v1/authentication`, the response codes of `POST /api/v1/flights` (404), `login` (400 and 404, not 401) and `refresh-token` (not 401), the bodies of the error responses (`CustomError`, and Spring's error body for some 400), the values of `httpStatus` (e.g., `OK`, not `200 OK`), and `application/json` as the media type of the responses (not `*/*`). It is not given to the tools by default. Details in `specifications/README.md`.

### Integration

- MongoDB in the container (6.0; the original repository runs `mongo:latest`, with no data), empty at each start. Until 2026-10, `database/init-mongo.js`, a script of the integration (not of the original repository, which has no data script), ran at each start: it created indexes and inserted 5 airports and 6 flights, but in collections that the API does not use (`airports`, `flights`, `users`, `tokens`, while the API uses `airport-collection`, `flight-collection`, `user-collection`, `invalid-token-collection`) and with other fields (`fromAirportId` and `toAirportId` instead of the airports of a flight), so the API never saw them (verified at runtime: "Couldn't find any airport"). It was removed: the runs start with an empty database, as they actually did before.
- The authentication by the proxy: as an ADMIN user, so that all the operations of the specification can be used, and with the renewal of its token, which expires after 30 minutes (see "Endpoints that may interfere with authentication").

## Endpoints that may interfere with authentication

RESTgym handles the authentication of the requests, and the tools are not aware of it: an endpoint that ends or changes the session of RESTgym (e.g., logout, login as another user, change or deletion of the user of the proxy, of its password or of its roles) may make the tools fail for the rest of the run. The proxy blocks the requests that would end its session (`471 Blocked by RESTgym`), instead of removing the endpoints from the specifications given to the tools.

When the API is ready, before the tools start, `entrypoint.sh` registers the administrator of the proxy (`POST /api/v1/authentication/user/register` with `userType: ADMIN`: email `restgym-proxy@restgym.com`, password `Password123!`); the container stops if it cannot (RESTgym then runs the run again). The proxy (`auth.py`) signs in as this administrator at the first request (again 5 seconds later if the sign-in fails), adds its access token to every request except those to `/api/v1/authentication/`, and signs in again 60 seconds before the token expires (the API gives tokens of 30 minutes, `accessTokenExpiresAt` in the answer of the login; `AUTH_ACCESS_TOKEN_EXPIRE_MINUTE`, fixed in its code), so the session lasts for any time budget. The proxy does not sign in again after a 401: the tools cannot invalidate the token of the proxy (see the logout below).

Verified at runtime (2026-10), on the image built from the current files: the administrator is registered at startup and the proxy signs in once; the operations of the administrator succeed through the proxy, also with an `Authorization` header of the tool (replaced), while the same requests straight to the API get 401; a registration of the email of the proxy gets 409; a tool can register, sign in and log out with its own tokens (forwarded); the logouts with the tokens of the proxy are blocked (471) whatever the form of the path (trailing or repeated slashes, `..`, percent-encoding, `;` parameters, query) wherever the token is in the body and however it is written (JSON escapes in the header, in the payload or in every character, UTF-16 with or without charset, EBCDIC, a BOM, content after the JSON, a duplicate key, the base64 alphabet, spaces around), also with the tokens found in the heap dump of the API, while the logouts with the other tokens of the heap dump are forwarded; the token of the proxy stays valid; after each of these, the proxy keeps working. The renewal was verified with a copy of `auth.py` that renews 20 seconds after signing in (instead of 60 seconds before the expiration): the proxy signed in again, the requests kept working with the new token, and the logouts with the access or refresh token of either sign-in were blocked, also with JSON escapes.

- **Registration before the tool**: the API rejects the registration of an email that already exists (`UserAlreadyExistException`, 409). Until 2026-10, the proxy registered `test@example.com` at the first request of the tool that was not to `/api/v1/authentication/`: a tool that registered `test@example.com` first (a common example email; the specification has no example) with its own password made the proxy unable to sign in ("Password is not valid!"), and every request got 401 for the rest of the run (reproduced at runtime, 2026-10, on that integration). Now the administrator of the proxy exists before the tool starts, and its email is one a tool would not choose: a registration of it by a tool gets 409 and changes nothing.
- **ADMIN**: the operations that create, update and delete airports and flights (`POST /api/v1/airports`, `PUT` and `DELETE /api/v1/airports/{id}`, `POST /api/v1/flights`, `PUT` and `DELETE /api/v1/flights/{id}`) require the ADMIN authority (`@PreAuthorize("hasAuthority('ADMIN')")`), and the others ADMIN or USER: as an administrator, the proxy can use all the operations of the specification. Until 2026-10, the proxy registered a USER, and these 6 operations answered 403 (`Access Denied`) to every request of the tools.

The endpoints that may end or change its session:

- `POST /api/v1/authentication/user/logout`: invalidates the access and refresh tokens in its body, whoever sends it (the endpoint is public: it needs no token, and does not check that the tokens belong to the sender; both tokens must be valid, and only they are invalidated, not the other sessions of the user; verified at runtime, 2026-10). The API invalidates a token by its id (`jti`, a random UUID), and only if the token is valid. No answer of the API contains the tokens of the proxy, but the heap dump of the API (`GET /actuator/heapdump`, served by the API, although not in the specification given to the tools) does: a tool could find them there and send them to the logout. With the tokens of the proxy, its session would end (every request answered 500, `Token is already invalidated!`) until the proxy signs in again (at the latest 30 minutes later). So the proxy blocks every logout whose body contains a token with the id of one of its tokens (of any access or refresh token it obtained during the run), answering it with `471 Blocked by RESTgym` and the header `X-RESTgym-Blocked: true`, without forwarding it to the API; the analysis counts them as blocked requests. It reads the body as the API does, so that no form of a token can get through: the strings of the JSON, with its escapes decoded (e.g., `\u0065` for `e`), in the charset of the `Content-Type` or the one detected (e.g., UTF-16), and only the first JSON value (Jackson ignores what follows); it compares the ids, also of tokens written with the base64 alphabet or with spaces around. The logouts with other tokens are forwarded as usual (verified at runtime, 2026-10).
- `POST /api/v1/authentication/user/login`, `POST /api/v1/authentication/user/register` and `POST /api/v1/authentication/user/refresh-token`: sign in, register other users and refresh tokens. They create other sessions, and do not end that of the proxy. A tool cannot sign in as the user of the proxy, since it does not know its password, nor register its email (see "Registration before the tool").
- No other endpoint is about users or authentication. The endpoints of Actuator do not change the session: `DELETE /actuator/caches` clears nothing (the API has no caches, `{"cacheManagers":{}}`), and `POST /actuator/loggers/{name}` changes the level of a logger.

## Known behavior of the API (kept as in the original)

- The original specification includes 25 operations of Spring Boot Actuator (`springdoc.show-actuator: true`, all its endpoints exposed), e.g., `POST /actuator/loggers/{name}` and `DELETE /actuator/caches`: removed from the specification given to the tools, but still served by the API.
- `GET /api/v1/airports` requires a request body, and its absence returns 400 (404 without the change of RESTgym), as does a body without `pagination` (500: `NullPointerException`).
- The API does not validate the tokens in the bodies of `POST /api/v1/authentication/user/logout` and `POST /api/v1/authentication/user/refresh-token`: a malformed, expired or foreign token returns 500 (exceptions of jjwt, e.g., `Invalid compact JWT string`).
- A request with a token invalidated by a logout returns 500 (`TokenAlreadyInvalidatedException: Token is already invalidated!`, thrown by the filter of the tokens, outside the handler of exceptions). It does not happen through the proxy, which replaces the token of every request with its own.
- An error whose answer cannot be written in a media type of `Accept` (e.g., `Accept: application/java-archive` with an invalid id) returns 500 (`HttpMediaTypeNotAcceptableException` while writing the answer of the handler), as in Spring.

## External services (verified 2026-10)

None. The API uses only the MongoDB of its container:

- **Code:** no class of the API uses a network client (HTTP, sockets, mail, messaging, cloud SDKs, tracing); its only URL is the link to the original repository. Of its libraries, `micrometer-registry-prometheus` only exposes the metrics for a Prometheus server to pull (`/actuator/prometheus`; no push gateway), and `spring-security-oauth2-client` has no client configured (no `spring.security.oauth2.client` in `application.yml`). `application.yml` imports an optional `.env` file, which does not exist in the container (the API runs in `/`).
- **Runtime**, on the image built from the current files of this repository, with a capture of all the traffic of the container except the requests to the proxy and the loopback: the container runs only the proxy (with `auth.py`), the API (MongoDB on `localhost:27017`) and MongoDB; no packet during the startup and 150 seconds idle, nor during requests to all the 40 operations of the standardized specification (also the 22 of Actuator).

## Known issues

- Until 2026-10, the API answered 401 or 404 to its errors (see [Changes made by RESTgym](#api)): the runs before that date have no 5XX, and are not comparable with the later ones in failures and status codes.
- Until 2026-10, the proxy signed in as a `USER` (`test@example.com`, registered at the first request), so the tools could not create, update or delete airports and flights (403), and it never renewed its token (30 minutes).
