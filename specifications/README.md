# Specifications of Flight Search API

## Original specification

`original/flight-search-openapi.json` (OpenAPI 3.0.1, JSON), unchanged.

- **Made by**: generated by springdoc-openapi 2.7.0 (in place of 2.1.0, which fails at runtime).
- **Source**: served by the API at `/v3/api-docs`, saved unchanged from the API running in its RESTgym container (2026-10).

The API has no specification file: its authors document it with springdoc-openapi, which generates the specification at runtime (`/v3/api-docs`) from the code and from the configuration of the API (`OpenApiConfig.java`: title, security scheme `bearerAuth`). The `pom.xml` of the original repository declares `springdoc-openapi-starter-webmvc-ui` **2.1.0**, which does not work with the Spring Boot of the API (**3.4.1**; springdoc supports Spring Boot 3.4 since 2.7.0): `GET /v3/api-docs` fails with `NoSuchMethodError: 'void org.springframework.web.method.ControllerAdviceBean.<init>(java.lang.Object)'`, which the security configuration of the API turns into 401.

To obtain the specification, RESTgym ran a copy of `flightsearchapi.jar` in which springdoc-openapi 2.1.0 was replaced by **2.7.0**, with the libraries it requires (swagger-core 2.2.25, swagger-ui 5.18.2, webjars-locator-lite 1.0.1, jspecify 1.0.0, from Maven Central; nothing else changed), and saved `/v3/api-docs` unchanged from the API running in its RESTgym container (2026-10). The copy was used only for this: the executable of the API in this repository is unchanged (it still contains springdoc-openapi 2.1.0 and swagger-core 2.2.9, verified 2026-10).

So the original is generated from the code and the configuration of the authors, but by a newer springdoc than the one they declare: details may differ from what a working 2.1.0 would generate. Its server URL is `http://localhost:8080` because springdoc writes the URL of the request, and RESTgym runs the API on port 8080 (the configuration of the API uses 1133).

## Standardized specification

`standardized/flight-search-openapi.json`: the original, formatted (indented with 2 spaces; the original is minified, on one line), with the change below. `standardized/flight-search-openapi.yaml` is the same specification in YAML, converted with yq 4.44.3 (the same content and order of properties, checked; see §6.4 of `docs/API-INTEGRATION-PROTOCOL.md` in RESTgym). The Swagger 2.0 version is converted from it (see below).

Changes from the original:

- **`in: header` removed from the security scheme `bearerAuth`** (validation error). `bearerAuth` is of type `http` (`scheme: bearer`, `bearerFormat: JWT`), and in OpenAPI 3.0 a security scheme of type `http` has only `type`, `scheme`, `bearerFormat`, `description` and extensions (`HTTPSecurityScheme`, with `additionalProperties: false`, in the official JSON Schema of OpenAPI 3.0): `in` belongs to the schemes of type `apiKey`. For `http`, the header is set by the standard (`Authorization: Bearer <token>`).
  - **Why**: the official Swagger Validator (swagger-validator-v2 2.1.9) reported on the original a schema error at `/components/securitySchemes/bearerAuth`: `instance failed to match exactly one schema (matched 0 out of 2)` (neither a reference nor a valid security scheme). Validated against the official JSON Schema of OpenAPI 3.0 (`https://spec.openapis.org/oas/3.0/schema/2021-09-28`), the original has this single error, and none without `in` (checked 2026-10).
  - **Where `in` comes from**: the configuration of the API (`OpenApiConfig.java` in the original repository) declares `@SecurityScheme(name = "bearerAuth", description = "JWT Token", scheme = "bearer", type = SecuritySchemeType.HTTP, bearerFormat = "JWT", in = SecuritySchemeIn.HEADER)`, and springdoc 2.7.0 writes `in` as declared.
  - **No change in meaning**: OpenAPI ignores `in` for schemes of type `http`, and the JWT goes in the `Authorization` header either way.
- **The 25 operations of Spring Boot Actuator removed** (40 operations in the original, 15 in the standardized specification): the 22 paths that start with `/actuator`, with all their operations:
  - `GET /actuator`; `GET /actuator/health`, `GET /actuator/info`; `GET /actuator/metrics`, `GET /actuator/metrics/{requiredMetricName}`, `GET /actuator/prometheus`; `GET /actuator/env`, `GET /actuator/env/{toMatch}`, `GET /actuator/configprops`, `GET /actuator/configprops/{prefix}`, `GET /actuator/conditions`, `GET /actuator/beans`, `GET /actuator/mappings`; `GET /actuator/threaddump`, `GET /actuator/heapdump`, `GET /actuator/scheduledtasks`, `GET /actuator/sbom`, `GET /actuator/sbom/{id}`; `GET /actuator/loggers`, `GET` and `POST /actuator/loggers/{name}`; `GET` and `DELETE /actuator/caches`, `GET` and `DELETE /actuator/caches/{cache}`.
  - **Why**: they are endpoints of the framework for monitoring and management, not operations of the API (infrastructure endpoints, rule 4 of the standardization in `docs/API-INTEGRATION-PROTOCOL.md` of RESTgym). They are in the original because the configuration of the API exposes all of them (`management.endpoints.web.exposure.include: "*"`) and documents them (`springdoc.show-actuator: true`). With them, the tools would spend a large part of their requests on operations that do not reflect the behavior of the API (25 of the 40 operations), and the coverage of the operations would count them. Also, `GET /actuator/heapdump` returns the memory of the API, with the tokens of the proxy of RESTgym in it (the proxy blocks the logouts with them anyway, see the README of the API).
  - The schema `Link` and the tag `Actuator`, used only by these operations, are kept: no operation uses them anymore.
  - The paths are still served by the API (its configuration is not changed).

**Swagger 2.0 version** (`standardized/flight-search-swagger.json`, and `standardized/flight-search-swagger.yaml`, the same in YAML): converted from `standardized/flight-search-openapi.json` with hidi 3.10.2, the command-line tool of Microsoft's OpenAPI.NET (`mcr.microsoft.com/openapi/hidi:3.10.2.202608213`, `hidi transform -v 2.0 -f json`); its output is only formatted with yq 4.44.3, and its YAML version is converted with yq (see §6.4 of `docs/API-INTEGRATION-PROTOCOL.md` in RESTgym). Checked against the OpenAPI 3 version: the same 15 operations, with the same parameters (name, location, required), request bodies and response codes, and the same 24 schemas, in the same order; it passes the official validation. What the conversion changes: the server becomes `host: localhost:8080` and `schemes: [http]` (no `basePath`, which means `/`); the schemas become `definitions`; the request bodies become `body` (or form) parameters, and the media types of the request bodies and responses become `consumes` and `produces`. Fixed after the conversion (validation error, rule 1 of the standardization): the security scheme `bearerAuth` (`type: http`, `scheme: bearer` in OpenAPI 3) has no equivalent in Swagger 2.0, and hidi leaves it empty ("bearerAuth.type is missing"): it is `type: apiKey`, `name: Authorization`, `in: header` (with its description), as Swagger 2.0 describes a bearer token. No operation uses it (the API authenticates with it, but the specification does not say so), and the proxy of RESTgym authenticates the requests anyway.

The official validation passes: `standardized/validation.json` (2026-10, swagger-validator-v2 2.1.9) has no messages.

## Corrected specification

`corrected/flight-search-openapi.json`: the standardized specification with the changes below, which make it match the implementation of the version packaged (commit `3de6a55` of the original repository, with the two classes changed by RESTgym, see the README of the API). The two files are identical except these changes: the same paths and operations, in the same order, and the same schemas, plus three new ones. `corrected/flight-search-openapi.yaml` is the same specification in YAML, converted with yq 4.44.3 (the same content and order of properties, read as YAML 1.2 and as YAML 1.1, checked; see §6.4 of `docs/API-INTEGRATION-PROTOCOL.md` in RESTgym). The Swagger 2.0 version is converted from it (see below). Each change was found in the source code of commit `3de6a55` and verified at runtime (2026-10, in the RESTgym container of the API, through the proxy and directly).

Changes from the standardized specification:

- **The paging request of `GET /api/v1/airports` and `GET /api/v1/flights` is a request body, not a query parameter**: the query parameter `request` (schema `AirportPagingRequest`, `required: true`) is replaced by a required JSON request body with the same schema.
  - **Why**: both controllers read it with `@RequestBody @Valid final AirportPagingRequest request` (`AirportController.getAllAirports`, `FlightController.getAllFlights`; the latter with `AirportPagingRequest` too, as the specification says). Verified at runtime: without a body, the API answers 400 `Required request body is missing`, whatever the query (e.g., `?pagination={"pageNumber":1,"pageSize":5}`, or `pagination[pageNumber]=1&pagination[pageSize]=5`); with the body `{"pagination": {"pageNumber": 1, "pageSize": 5}}`, 200 (or 404 when there is no airport).
  - A request body in a `GET` is unusual: OpenAPI 3.0 allows it, but warns that its semantics are not defined by HTTP, so some tools and clients may not send it.
- **`pagination`, and its `pageNumber` and `pageSize`, are required** (`required` added to `AirportPagingRequest`, `SearchFlightRequest` and `CustomPaging`).
  - **Why**: `CustomPagingRequest.toPageable()` reads them without checking them (`pagination.getPageNumber()`, `pagination.getPageSize()`), and the field `pagination` has no `@Valid`. Verified at runtime: without `pagination` (`GET /api/v1/airports` with `{}`, `POST /api/v1/flights/search` without it), or without `pageSize`, the API answers 500 (`NullPointerException`). The `minimum: 1` of both is already in the specification, though the API does not validate it either (`pageNumber` 0: 500 `Page index must not be less than zero`).
- **The path parameter `id` is a UUID** (`format: uuid` added to `id` in the 6 operations of `/api/v1/airports/{id}` and `/api/v1/flights/{id}`).
  - **Why**: the controllers declare it `@PathVariable @Valid @UUID final String id`. Verified at runtime: any other value gets 400 (`must be a valid UUID`), a UUID of no airport 404, and the id of an airport 200. The ids that the API creates and returns (e.g., by `POST /api/v1/airports`) are UUIDs.
- **The dates of the search are dates, not date-times** (`format: date` instead of `date-time` for `departureTime` and `arrivalTime` of `SearchFlightRequest`).
  - **Why**: both are read by `CustomLocalDateTimeDeserializer`, which appends `T00:00:00` to the value and parses the result as a local date-time (with `@JsonFormat(pattern = "yyyy-MM-dd")`). Verified at runtime: `"departureTime": "2026-11-01"` gets 200, and a date-time (`"2026-11-01T00:00:00Z"`) 400 (`Text '2026-11-01T00:00:00ZT00:00:00' could not be parsed`). The dates of `CreateFlightRequest` and `UpdateFlightRequest` are date-times, as the specification says.
- **The email of `RegisterRequest` is an email address** (`format: email` added).
  - **Why**: the field has `@Email(message = "Please enter a valid e-mail address")`. Verified at runtime: `"email": "test35583"` gets 400 with this message. The email of `LoginRequest` has only `@NotBlank`, and is not changed.
- **The bearer token is required by the 11 operations outside `/api/v1/authentication`** (`security: [{bearerAuth: []}]` added to each; the security scheme `bearerAuth` was already declared, but no operation used it).
  - **Why**: `SecurityConfig` permits without authentication only `POST /api/v1/authentication/**` (and the paths of the documentation and of Spring Boot Actuator, not in this specification); every other request must be authenticated (`anyRequest().authenticated()`). Verified at runtime: without a token, `GET /api/v1/airports/{id}` gets 401; with the token of a `USER`, 200, and `DELETE /api/v1/airports/{id}` 403 (only `ADMIN`). In RESTgym the proxy authenticates every request anyway (see the README of the API).
- **The response codes of three operations**, as the code answers them (the descriptions of the codes added are new):
  - `POST /api/v1/flights`: 404 added (`Airport not found`): `FlightCreateServiceImpl` throws `AirportNotFoundException` when an airport of the flight does not exist (verified: 404 `Departure airport not found with id ...`).
  - `POST /api/v1/authentication/user/login`: 401 removed, 400 and 404 added. `LoginServiceImpl` throws `UserNotFoundException` (404) for an unknown email and `PasswordNotValidException` (400) for a wrong password, and the validation of the request answers 400; nothing answers 401 (the path is permitted without authentication). Verified: 404 `User not found!`, 400 `Password is not valid!`, 400 `Validation failed` (blank email and password).
  - `POST /api/v1/authentication/user/refresh-token`: 401 removed. A malformed, expired or foreign token is not handled by the API (the exceptions of jjwt are not of its package): 500 (verified: `Invalid compact JWT string`), a bug of the API kept as it is (see the README of the API); the validation answers 400 (verified: blank token).
- **The bodies of the error responses** (every response but 200, in all the operations): `CustomError` instead of the `CustomResponse...` of the operation, and for 400 either `CustomError` or `SpringError` (`oneOf`). Three schemas are added: `CustomError` and `CustomSubError` (the error of the API: `time`, `httpStatus`, `header`, `message`, `isSuccess`, `subErrors` with `message`, `field`, `value`, `type`), and `SpringError` (the error body of Spring: `timestamp`, `status`, `error`, `message`, `path`).
  - **Why**: the handler of exceptions of the API (`GlobalExceptionHandler`) and its entry point of authentication (`CustomAuthenticationEntryPoint`, 401) answer a `CustomError`, not a `CustomResponse`; the errors that the API leaves to Spring (since the change of RESTgym, e.g., an unreadable or missing body) have the body of Spring. Verified at runtime: e.g., 400 `{"time": ..., "httpStatus": "BAD_REQUEST", "header": "VALIDATION ERROR", "message": "Validation failed", "isSuccess": false, "subErrors": [{"message": "must not be blank", "field": "refreshToken"}]}`, 401 `{"time": ..., "httpStatus": "UNAUTHORIZED", "header": "AUTH ERROR", "isSuccess": false}`, and 400 `{"timestamp": ..., "status": 400, "error": "Bad Request", "message": "JSON parse error: ...", "path": "/api/v1/airports"}`.
- **The values of `httpStatus`** (in the 7 `CustomResponse...` schemas, and in the new `CustomError`): the names of the constants of Spring's `HttpStatus` (e.g., `OK`, `NOT_FOUND`) instead of `200 OK`, `404 NOT_FOUND`, ... (the same 69 values, in the same order).
  - **Why**: Jackson writes an enum with the name of its constant; springdoc documents it with `HttpStatus.toString()`. Verified at runtime: every response has, e.g., `"httpStatus": "OK"`, never `"200 OK"`.
- **The media type of every response is `application/json`**, instead of `*/*` (as springdoc writes it when the controllers declare no `produces`).
  - **Why**: the API writes every answer in JSON: the results of the controllers and the errors of its handler with Jackson, the 401 of its entry point with `Content-Type: application/json`, and the errors left to Spring with the JSON error body. Verified at runtime, with `Accept: */*`, `Accept: application/json` and without `Accept`: successes, 400 and 404 of the handler, 400 and 500 of Spring, 401 and 409, all `application/json`. Only a client that does not accept JSON gets something else, from Spring, not from the API: with `Accept: text/html`, an HTML error page (406 instead of a success, 500 instead of the errors of the handler, 400 and 500 of Spring), and with `Accept: application/xml` or `text/plain` the same status codes with an empty body; the 401 is JSON in every case.

Not changed, though they do not describe the API exactly:

- The date-times of the API (`time` of every response, the dates of flights) have no offset (e.g., `2026-10-29T15:28:22.747635466`), while `format: date-time` requires one; in requests, the API accepts a date-time without offset or with `Z`, but not with another offset (400 for `2026-11-01T10:00:00+02:00`). OpenAPI 3.0 has no format for a local date-time.
- The 500 that some requests get (e.g., a malformed token in `logout` or `refresh-token`, a missing `pagination`) are bugs of the API, not documented responses.

**Swagger 2.0 version** (`corrected/flight-search-swagger.json`, and `corrected/flight-search-swagger.yaml`, the same in YAML): converted from `corrected/flight-search-openapi.json` with hidi 3.10.2, as the standardized one (`mcr.microsoft.com/openapi/hidi:3.10.2.202608213`, `hidi transform -v 2.0 -f json`); its output is only formatted with yq 4.44.3, and its YAML version is converted with yq. Checked against the OpenAPI 3 version: the same 15 operations, with the same parameters (name, location, required), request bodies, response codes and security, and the same 27 schemas, in the same order; it passes the official validation. What the conversion changes is the same as for the standardized version (server, `definitions`, `body` parameters, `consumes` and `produces`); the request bodies of `GET /api/v1/airports` and `GET /api/v1/flights` become `body` parameters too. Fixed after the conversion, as in the standardized version: the security scheme `bearerAuth`, which hidi leaves empty, is `type: apiKey`, `name: Authorization`, `in: header` (with its description). Approximated: Swagger 2.0 has no `oneOf`, and hidi writes the body of the 400 responses as `allOf: [CustomError]` (`SpringError` is lost).

The official validation passes: `corrected/validation.json` (2026-10, swagger-validator-v2 2.1.9) has no messages.

## Endpoints of the original that may interfere with authentication

The proxy of RESTgym registers `test@example.com` (username `testuser`, password `Password123!`) as an **ADMIN** user (`"userType": "ADMIN"`), signs in at the first request, and adds its access token (JWT) to every request except those to `/api/v1/authentication/` (`auth.py`).

- **ADMIN**: the operations that create, update and delete airports and flights (`POST /api/v1/airports`, `PUT` and `DELETE /api/v1/airports/{id}`, `POST /api/v1/flights`, `PUT` and `DELETE /api/v1/flights/{id}`) require the ADMIN authority (`@PreAuthorize("hasAuthority('ADMIN')")`), and the others ADMIN or USER: as an ADMIN user, the proxy can use all the operations of the specification. Until 2026-10, the proxy registered a USER, and these 6 operations answered 403 (`Access Denied`) to every request of the tools, so that the tools could never create airports and flights. Verified at runtime (2026-10): with the ADMIN user, `POST /api/v1/airports` answers 200.
- **Token renewal**: the access tokens of the API expire after 30 minutes (`AUTH_ACCESS_TOKEN_EXPIRE_MINUTE`, fixed in the code of the API, `ConfigurationParameter`: it cannot be changed by configuration). The proxy reads the expiration of its token (its `exp` claim) and signs in again when it expires within 60 seconds, so that its session lasts for the whole run. Until 2026-10, the proxy signed in only once, and its token expired after 30 minutes: every later request of a run got 401. Verified at runtime (2026-10, with a renewal margin of 1795 seconds, so that the proxy signs in again every 5 seconds): the requests keep working across the renewals.

The endpoints that may end or change its session:

- `POST /api/v1/authentication/user/logout`: invalidates the access and refresh tokens in its body. The tools never see the token of the proxy (the proxy adds it, and no response contains it), so they can only invalidate tokens they obtained themselves; with the token of the proxy, its session would end until the proxy signs in again (at the latest 30 minutes later).
- `POST /api/v1/authentication/user/login`, `POST /api/v1/authentication/user/register` and `POST /api/v1/authentication/user/refresh-token`: sign in, register other users and refresh tokens. They create other sessions, and do not end that of the proxy. A tool cannot sign in as the user of the proxy, since it does not know its password.
- No other endpoint is about users or authentication. The endpoints of Actuator (not in the standardized specification, but served by the API) do not change the session: `DELETE /actuator/caches` clears nothing (the API has no caches, `{"cacheManagers":{}}`), and `POST /actuator/loggers/{name}` changes the level of a logger.
